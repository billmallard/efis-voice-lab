# M2 notes: retrieval service (2026-10-09)

## Shape

```
lab/retrieval/core.py        Retriever.search(query, k, filters) / get_source(repo, path)
lab/retrieval/mcp_server.py  FastMCP "efis-docs": search_docs, get_source   (lab serve-mcp [--http PORT])
lab/retrieval/rest_api.py    FastAPI: POST /search, GET /source, GET /healthz (lab serve-api)
```

Both interfaces are thin adapters over one `Retriever`, so they agree by construction. That is
still checked end to end, because "by construction" is a claim a test should back up.

- **Filters:** `origin` (fork | upstream), `repo`, `doc_type`. `k` is capped at 20.
- **Deterministic order:** hits are sorted by (score desc, point id), so equal scores can't
  reorder between calls.
- **Responses carry their own provenance:** embedding model, collection, and a timing split
  (embed / search / total). L1 can attribute latency without extra instrumentation.
- **Auth:** if `LAB_API_TOKEN` is set, REST requires `Authorization: Bearer …` everywhere except
  `/healthz`. Unset locally. It must be set before the API goes behind a tunnel (M8, D2).
- **Errors:** `get_source` on an unknown document returns 404 over REST and a `ToolError` over
  MCP. That is an expected, client-facing failure, so the server logs no traceback.
- **Claude Code integration:** the repo's `.mcp.json` registers `efis-docs` (`uv run lab serve-mcp`),
  so opening the repo in Claude Code offers the tools.

## Acceptance results (local, full corpus, CPU embedding)

`scripts/check_retrieval.py` starts `lab serve-api` (uvicorn) and `lab serve-mcp` (stdio)
as separate processes, then sends 20 questions (the golden starter set plus FIX-Gateway probes)
through both:

| Measure | n | p50 | p95 | max |
|---|---|---|---|---|
| Server-side search (embed + Qdrant) | 40 | 79 ms | 96 ms | 101 ms |
| REST round trip | 100 | 81 ms | 98 ms | 139 ms |
| MCP round trip (stdio) | 20 | 84 ms | 95 ms | 100 ms |

- All 20 queries returned identical hits (same ids, same order, scores within 1e-6, identical
  payloads), and so did `get_source`.
- The p95 budget is 300 ms; the measured p95 is 98 ms. Query embedding is nearly all of it.
  The Qdrant search itself takes single-digit milliseconds.
- From an MCP client: headless Claude Code (`claude -p --mcp-config .mcp.json`, Haiku) called
  `search_docs` and answered "GPL-2.0-or-later — billmallard/pyEfis, fork, README.rst, 6d8fa2d".
  That took 3 turns and cost $0.09.

**Tail latency is sensitive to host load.** One run straight after a `uv sync` showed REST
p95 440 ms (max 1.4 s) while the server-side p95 stayed at 98 ms. Three immediate re-runs
passed at 100–139 ms. So L1 should take p95 over repeated passes and record the host's state, and
a single spike should not count as a regression.

CI runs the same check against its two-source index with a 1,500 ms budget. A shared runner is
not the lab host, so CI guards correctness and the local run guards latency.

## Top-1 observations for M3

Raw top hits for the starter questions. This is *not* the L1 score (gold sources come in M3), but it
shows where the golden set will have teeth:

- **Look-alike internal docs win:** "Do I need a GPU" → `docs/perf_baseline_gpu_required.md`;
  "Which install extras are required?" → `docs/screenbuilder.md`, where the README is expected.
- **Cross-repo answers:** "How much storage does the North America terrain set need?" →
  makerplane-data `docs/terrain.md`, where the plan expected pyEfis README.rst (HW-005). "Where
  does the SVS terrain data come from?" → makerplane-data `docs/svs_runway_terrain.md`. Both may
  be *legitimate* gold sources. M3 should allow several gold sources per question rather than
  assume the README is canonical.
- **Config YAML as an answer:** "Is SVS on by default and how do I enable it?" →
  `src/pyefis/config/includes/ahrs/svs.yaml`. A config file is a fine *source*, but it is the hardest
  kind of text to speak aloud, which makes it a good speakability case for L2.
