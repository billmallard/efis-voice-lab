# D1 notes: published test report

The report is public at https://efis-voice-lab.pages.dev. CI renders it from the run
records committed under `runs/` and deploys it to Cloudflare Pages: `main` goes to the
public site, and every other branch gets a preview at `<branch>.efis-voice-lab.pages.dev`.

## The split: the lab host runs the suites, CI publishes them

Full runs can't happen on a CI runner. The agent under test is llama3.1:8b on a local GPU,
the judge needs an API key and costs about $2 for all three layers, and L3 takes about 70
minutes. CI already runs every suite as a harness check (tiny model, judge off), but those
numbers say nothing about quality. So the plan's "CI deploys it" is taken literally: CI
renders and deploys, and the runs come from the lab host.

- **`lab publish L1 L2 L3`** (lab host) copies each layer's `results/<layer>/latest.json`
  to `runs/<layer>/<stamp>.json`, where the stamp is the run's start time. `--from`
  publishes an older run file.
- **Audio stays out of git.** An L3 run has 172 WAVs, about 87 MB. `publish` encodes them
  to 40 kbps MP3 (9.9 MB) and attaches them as `audio.zip` to a GitHub release tagged
  `audio-L3-<stamp>`, marked not-latest. The run JSON is unchanged; the site build finds
  the release by the naming convention. Encoded files are cached under
  `results/audio-cache/`, so a local build doesn't download them again.
- **`lab site`** (CI) loads every published run, re-attributes L2 and L3 with the current
  rules (as `lab report` already did), fetches the newest L3 run's audio, and renders
  `site/`. It needs only the base dependencies, so the job takes about a minute.

Only the newest run of each layer gets the drill-down; older runs contribute to the trend
charts and the runs table. A release per run keeps each run's audio available if per-run
pages are wanted later.

## What the page adds over `lab report`

- **The change since the previous run** on every headline number: an arrow, the amount,
  and green or red by whether it got better. Latency counts lower as better. This is what
  makes a regression visible at a glance.
- **History:** one small chart per headline metric, oldest to newest, with the threshold
  as a dashed target line. Each is single-series, so there's no legend; the end value is
  labeled, and hovering a point shows its time, commit and case count.
- **Runs table:** every published run with layer, case count, lab commit (linked), agent
  model, headline metric and judge cost. It's also the table view of the charts.
- **Metadata:** corpus repos with their pinned SHAs, and a footer naming the commit and
  branch CI built from.

`lab report` still renders just the latest local runs to `results/report/`. Both share
`report.build`, and the metrics come from one table (`report.METRICS`), so the cards, deltas
and charts can't disagree.

## Cloudflare

- Pages project `efis-voice-lab`, production branch `main`.
- Wrangler 4.149 hands `pages project create` to Workers static assets, and that path
  fails on a directory upload. The project was created once with `--force` to stay on
  classic Pages; deploys after that run against Pages directly and need no flag.
- CI deploys with `wrangler pages deploy` when the `CLOUDFLARE_API_TOKEN` and
  `CLOUDFLARE_ACCOUNT_ID` secrets are set. The token needs only Account > Cloudflare Pages >
  Edit. Without them, the job still builds the site, uploads it as an artifact and
  leaves a notice.
- A new project's `*.pages.dev` certificate takes a few minutes after the first deploy;
  until then browsers fail with `ERR_SSL_VERSION_OR_CIPHER_MISMATCH`.
